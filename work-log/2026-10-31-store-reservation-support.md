# 매장 상세의 예약 지원 여부 제공

- 작업일: 2026-10-31
- 관련 명세: [주변·인기 매장](https://app.notion.com/p/3d548d76fa3281f48332fa1379c975c8), [공공 매장 경계](../docs/frontend/feature-1-public-store-boundaries.md)
- 기준: `dev`의 `342f86e8fe3ab9e1874806f1ffd7f85a787bfaa6`

## 배경과 판단

공공 매장도 고객 상세 조회는 가능하지만 예약 가용성과 예약 생성은 지원하지 않는다. 화면이 영업시간·테이블 유무로 이를 추측하면 불필요한 조회와 예약 진입이 생긴다. 상세 응답에 지원 여부를 제공하고, 프런트에서 예약 버튼을 비활성화하고 사유를 표시하는 방향을 승인받았다.

`reservationEnabled`는 점주가 연결된 매장이면 `true`, `owner_id NULL` 공공 매장이면 `false`다. 날짜별 영업 여부나 현재 남은 테이블 수를 뜻하지 않는다. 테이블이 없는 점주 매장도 지원 여부는 `true`이며, 실제 예약 가능 여부는 기존 가용성·생성 API가 판단한다.

## 실제 변경

- `StoreDetailResponse`와 변환 함수에 `reservationEnabled`를 추가했다.
- 점주 매장과 공공 매장 상세 테스트에 값을 검증했다. 공공 매장에 테이블·영업시간이 남아 있어도 `false`임을 확인했다.
- 기존 공공 매장 쓰기 제한, 회원 식별, 예약 상태·테이블 잠금·시간 중복 제약과 스키마는 변경하지 않았다.

| --- | --- | --- |

| 실제 프런트 연동 | 별도 앱 DB `catchtable_integration_app`, 백엔드 18080·프런트 15173, `VITE_API_MOCKING=false`, 새 브라우저 컨텍스트 | 공공 매장 상세의 `false`, 예약 버튼 비활성화·사유, 가용성 요청 없음, 직접 예약 경로 차단 확인 |
| 관련 예약 회귀 | 같은 합성 데이터 환경 | 검색 조건 유지 후 실제 예약 201, 경쟁 예약 201 뒤 원요청 409와 시간 재선택 확인 |

기존 컨테이너·공용 DB·원래 작업 폴더의 변경은 검증 대상으로 사용하지 않았다. CI·배포·외부 결제는 확인하지 않았다.

## 남은 점

Notion API 정본에 추가 조회 필드 반영이 필요하다. 프런트 전체 검증과 별도 발견 사항은 프런트 작업 기록에 구분한다. CI·배포 결과는 이 로컬 검증과 구분한다.
