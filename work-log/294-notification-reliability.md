# 고객 순번 갱신과 알림 재시도 수정

2026-11-23. [#294](https://github.com/Techeer-2026-2-E/catchtable-backend/issues/294) · [PR #298](https://github.com/Techeer-2026-2-E/catchtable-backend/pull/298). [환불 테스트 수정](294-refund-notification-test.md) 이후, 실제 취소 서비스와 알림 워커를 PostgreSQL 16.15에서 함께 실행해 남아 있던 경합을 확인했다.

## 제품 변경

- 두 팀 중 첫 팀이 취소될 때 기존 순번 갱신이 취소 커밋보다 일찍 끝나면 남은 팀의 현재 순위는 1위인데 SSE에는 2위만 남았다. 미완료 작업은 0개였다. 같은 매장·날짜의 대기 작업에 변경을 합칠 때 해당 행을 커밋까지 잠그고, 워커는 `SKIP LOCKED`로 건너뛴다. 같은 점주 갱신에도 적용한다. [작업 저장소](../src/main/java/com/catchtable/notification/repository/NotificationJobRepository.java)
- 처리권이 만료된 작업을 다시 가져갔을 때 이전 시도의 `NO_CONNECTION`이 새 시도의 `SENT`를 막을 수 있었다. 완료 시 작업 ID·시도 번호·처리 상태를 함께 잠그고 검사한다. 오래 걸리는 전송은 처리권을 확인하고 연장한다. 재시도 한도를 소진한 작업과 새 순번 갱신에 흡수된 작업도 회귀 검사에 포함했다. [처리 코드](../src/main/java/com/catchtable/notification/job/NotificationJobProcessor.java) · [시도별 회귀 검사](../src/test/java/com/catchtable/notification/job/NotificationJobAttemptTest.java)
- 서로 다른 회원의 직접 알림은 앱당 최대 2건이 진행된다. 같은 회원의 다음 작업은 앞선 작업이 끝난 뒤에 처리한다. 실제 SSE 쓰기는 직접 알림과 점주·순번 갱신 각각 4슬롯, 기본 500ms 대기 제한을 사용한다. 한 회원의 쓰기를 대기시킨 테스트에서 다른 회원의 전송과 `SENT` 기록이 먼저 끝났다. 기한 안에 결과가 없거나 슬롯이 모두 사용 중인 경우에는 확인되지 않은 전송을 성공으로 기록하지 않는다. 수치는 초기 실행 설정이다. [연결 쓰기](../src/main/java/com/catchtable/notification/job/SseConnectionWriter.java) · [전송 계약](../docs/waiting-sse-durability.md)
- 대기 상태를 바꾸기 전 워커가 먼저 작업을 가져갈 수 있던 테스트 준비 순서를 고쳤다. 실제 전송 결과와 `DONE`을 검사하고, 커밋 후 알림을 깨우는 동작은 테스트가 별도로 워커를 깨우지 않아도 성립하는지 확인한다.

## 격리 검증

| 검사 | 결과 |
| --- | --- |
| 커밋 경합 | 수정 전에는 취소 트랜잭션이 끝나기 전에 별도 연결에서 순번·점주 작업을 가져갔다. 수정 후에는 두 작업을 모두 건너뛰고 커밋 후 남은 고객에게 정확히 1위를 전달했다. |
| 다른 회원 전송 | 수정 전 커밋 `d610e2c`에서는 첫 회원의 모의 쓰기를 대기시키면 두 번째 회원의 전송 검사가 실패했다. 수정 후 같은 조건에서 두 번째 회원의 전송은 끝나고 첫 회원의 다음 알림은 순서를 지켰다. 경로별 쓰기 한도·타임아웃·허가 반환도 검사했다. 실제 고객 네트워크의 지연 시간은 측정 범위 밖이다. |
| 전체 빌드 | 수정한 제품 소스를 깨끗한 디렉터리에 복원하고 Java 21·빈 PostgreSQL 16.15에서 `./gradlew --offline --max-workers=2 build` 실행. 1,193건 통과, 실패·오류·건너뜀 각 0건. |
| 역사적 측정기 | 고도화 전 앱을 `a44952e`로 고정한다. 점주 호출은 시도·HTTP 200·실패를 구별하고, 전체 구독자가 접속해야 하는 실험은 실제 접속·종료 시각을 호출 구간과 대조한다. 표본이 부족한 경우 JSON에 `valid=false`를 남긴다. [측정 절차](../scripts/notification-loadtest/README.md) |

실제 k6 스모크에서는 localhost에 구독 한 개와 점주 호출 한 건을 두었다. 자동 선택된 k6 2.4.0과 확장 0.2.0에서 이벤트 핸들러를 연결할 수 없어 기존 측정 조합인 k6 2.1.0과 확장 0.2.0을 고정했다. 정상 응답은 성공 1건·유효, 409 응답은 성공 0건·실패 1건·측정 불충분으로 구분됐다.

## 열린 PR의 마이그레이션

원격 `dev@1f51158`의 최신 파일은 V40이다. 검색 #292·#293·#295와 알림 #291·#298, Redis #297의 서로 다른 SQL이 V41·V42·V43에서 겹친다. #290은 SQL 추가가 없다. #298에는 열린 작업 조회용 인덱스를 V43.4로 추가했었다. 복원 테스트도 Flyway가 사용하는 버전 비교기로 점으로 구분된 버전을 정렬한다.

2026-11-23에 아래 번호를 #291·#297·#298 브랜치에 반영했다. SQL 본문은 바꾸지 않았다. 공유 DB는 EC2 배포(#277, 2026-11-13)뿐이고 이 PR들은 2026-11-22에 만들어져 V41 이상이 적용됐을 가능성은 낮다. 다음 배포 전에 아래 읽기 전용 조회로 EC2 이력이 V40 이하인지 확인한다.

| 출처 | 이전 파일 버전 | 반영한 버전 |
| --- | --- | --- |
| #291 알림함 | V41 | V40.1 |
| #298 알림 작업·인덱스 | V43 · V43.4 | V40.2 · V40.3 |
| #292 · #293 · #295 검색 | V41 · V42 · V43 | V41 · V42 · V43 |
| #297 Redis 선행 3개 | V41 · V42 · V43 | V43.1 · V43.2 · V43.3 |
| #297 후속 12개 | V44~V55 | V44~V55 |

격리 DB에서 SQL 본문을 그대로 사용해 dev V40 → #291 → #298 → #290 → #292 → #293 → #295 → #297 순서로 적용했다. 각 단계에서 기본 순서 검사와 Flyway validate가 성공했다. dev 단계에서 넣은 테스트 회원은 마지막까지 보존됐고, 최종 V55에서 다시 migrate한 결과 추가 적용은 0건이었다. 전 PR의 소스를 합친 로컬 후보에서도 예약·접수·환불·알림·매장 검색 관련 검사 94건이 통과했다. #293의 테스트 설정은 인기 점수 스케줄러와 알림 워커 안전망 설정을 함께 보존하고, #297의 프로젝트 문서에는 Redis와 새 알림 계약을 함께 남겼다.

보존 대상 DB에서는 앱이 실제 사용하는 스키마의 이력을 아래 읽기 전용 조회로 확인한다. 성공 행의 버전·파일명·체크섬뿐 아니라 실패 행과 순서도 함께 대조한다. 보존할 DB에 이전 번호로 적용한 행이 있으면 해당 이력을 가진 복제본으로 별도 업그레이드 경로를 검증해야 한다. 이번 작업의 DB 검사는 전용 컨테이너에서 수행했다.

```sql
BEGIN READ ONLY;
SELECT current_database(), current_schema();
SELECT installed_rank, version, script, checksum, success
FROM flyway_schema_history
ORDER BY installed_rank;
ROLLBACK;
```

## 재검토 후 실제 출력 확인

호출자가 기다리는 시간만 제한하면 아직 쓰기 중인 연결이 전송 슬롯을 계속 차지할 수 있었다. 고객·점주 구독에 서블릿 비차단 출력을 적용했다. 초기 인사만 작은 버퍼에 보관하고, 컨테이너의 첫 쓰기 가능 콜백에서 연결을 공개한다. 이후에는 준비된 출력에만 최대 8KiB씩 쓰며 프레임 전체에 같은 기한을 사용한다. 기한을 넘기면 그 async 요청을 끝내고, 대기한 전송 스레드도 반환한다. [서블릿 출력](../src/main/java/com/catchtable/notification/job/SseServletOutput.java)

실제 내장 Tomcat의 고객·점주 구독 주소 각각에서 `connect` 인사와 커밋 후 업무 이벤트를 받았다. 쓰기 준비가 끝까지 오지 않는 서블릿 출력 두 개를 둔 별도 회귀 검사에서는 두 요청의 종료와 같은 풀에서 다음 정상 연결의 전송을 확인했다. 실제 운영망 부하 수치와 구분한다. 재검토 회귀 검사에는 서버가 감싼 쓰기 시간 초과도 포함된다. 최종 검사 수와 실행 결과는 PR의 해당 커밋 CI에서 확인할 수 있다. [HTTP 검사](../src/test/java/com/catchtable/notification/job/SseSubscriptionHttpTest.java) · [출력 기한 검사](../src/test/java/com/catchtable/notification/job/SseServletOutputTest.java)

재접속 실험에서는 모든 구독이 403인데 점주 호출만 200인 조건도 루프백에서 재현했다. 구독을 시도한 횟수와 연결 인사를 비교하고 각 고객의 첫 연결을 확인해, 정상 재접속은 유효, 전원 403은 측정 불충분과 k6 종료 코드 99로 판정했다. [재접속 시나리오](../scripts/notification-loadtest/exp3-reconnect-gap.js)

번호 후보는 #291·#297·#298 독립 소스에서도 필요한 테스트 버전 비교기를 함께 적용해 마이그레이션·시드 검사 각 19건이 통과했다. 7개 통합 소스의 마이그레이션·시드 검사도 19건이 통과했다. 기존 번호 V41·V43으로 만든 #298 DB 사본에서는 신규 V43.4만 적용되고 체크섬과 미처리 알림이 보존됐다. 같은 이력에 번호 후보만 바꿔 적용 전 검증을 하면 Flyway가 거부했다.
