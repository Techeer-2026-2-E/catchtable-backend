# 웨이팅 장부 커밋과 대기표 HTTP 응답

2026-11-22 KST. `dev@1f51158fbfda6871737368242ba57318e25326f7`에서 분리한 `feat/waiting-intake`의 로컬 구현이다. 0차에서 선택한 **PG가 수락 순번을 확정하고 커밋 후 대기표를 응답하는 최소 경로**를 기존 고객 POST에 연결했다. 웨이팅 번호 발급·취소 워커가 연결되기 전이므로 이번에 설정한 매장·접수일은 모두 격리 시험 DB 안에 있다. [기존 팀 API 명세](https://app.notion.com/p/fbf48d76fa3282e1a946818c8cba1f3d) · [실행 절차](../tools/waiting-intake-benchmark/README.md)

## HTTP 계약

| 조건 | 응답 |
| --- | --- |
| 매장·서울 접수일 장부 설정 없음 | 기존 POST 그대로 신규 201·같은 활성 신청 200·인원 충돌 409. 실제 `waitingId/waitNumber/teamsAhead`와 기존 이벤트를 발급 |
| 장부를 켠 매장·접수일에 최초 POST | `X-Member-Id`와 클라이언트 생성 `Idempotency-Key` 사용. 커밋 후 HTTP 202, `Location: /api/user/waitings/receipts/{receiptId}`, 시험용 `Retry-After: 2`초 |
| 응답을 못 받은 고객이 같은 회원·키·본문으로 재전송 | HTTP 200, 같은 대기표·최초 수락 순번·Location. 기존 키 조회는 오늘 날짜와 매장 마감·한도 검사보다 먼저 수행 |
| 같은 회원·매장·접수일, 다른 키·같은 인원 | 원래 대기표를 200으로 반환하고 별칭 키도 같은 표에 연결. 같은 키의 다른 매장/인원은 409, 같은 활성 신청의 인원 충돌도 409 |
| 신규 신청에서 장부가 가득 참 | 429 `WAITING_INTAKE_FULL`과 `Retry-After`. 키·순번·미완료 수에 부분 기록을 남기지 않는다 |
| 상태 조회 | `GET /api/user/waitings/receipts/{receiptId}`에 회원 헤더를 사용한다. 본인 200·다른 회원 또는 없는 표 404. 현재 상태는 `PENDING`이며 조회가 순번을 바꾸지 않는다 |

예를 들어 회원이 2인 웨이팅을 신청하면 기존 본문 `{"storeId":1,"partyCount":2}`를 보낸다. 장부 응답 예시는 다음과 같다.

```json
{
  "receiptId": "6240b329-160b-401a-b0da-4aa1bf5b0d53",
  "storeId": 1,
  "receivedDate": "2026-11-22",
  "intakeSequence": 1,
  "partyCount": 2,
  "status": "PENDING"
}
```

이 단계의 ON 응답은 한가한 매장도 대기표를 발급한다. 실제 식당 번호·앞 팀 수·최종 처리 시간은 후속 등록 단계에서 확인해야 한다. 키는 1~128자 공백 없는 가시 ASCII 문자열로 검증한다. 현재 회원 식별은 기존 목 헤더 계약을 따른다.

## 저장과 경합

- V41은 매장·일자별 수용량/미완료 수/마지막 수락 순번, 회원 소유 대기표, 재시도 키 매핑을 추가한다. 마이그레이션만 적용하면 활성 매장·일자는 0개다. V42는 장부 일자 개설과 기존 등록을 같은 매장 락으로 직렬화하고 레거시 등록 이력이 있는 날의 중도 개설을 거부한다. 키 없는 기존 Java 서비스 진입점도 설정된 날에 직접 등록할 수 없다. [장부 스키마](../src/main/resources/db/migration/V41__create_waiting_intake_ledger.sql) · [경로 전환 가드](../src/main/resources/db/migration/V42__guard_waiting_intake_day_activation.sql)
- 같은 회원의 키·별칭 경합은 회원 행의 `FOR NO KEY UPDATE`로 정리한다. 매장별 영업 상태·기존 활성 웨이팅·영업시간과 인원(1~20)을 확인한 뒤 매장·일자 행의 조건부 UPDATE로 용량과 수락 순번을 함께 배정한다. 다른 회원의 다른 매장은 같은 카운터를 사용하지 않는다.
- 새 대기표에는 해당 회원·키 바인딩을 같은 SQL에 넣었다. PG가 커밋을 완료하고 Spring 트랜잭션이 반환한 뒤 컨트롤러가 202를 만든다. 롤백되면 고객의 키·표·카운터 갱신이 함께 취소된다. 접수 순서는 `intakeSequence`로 확인한다. 클라이언트 클릭이나 HTTP 응답 도착 시각으로 순서를 판정하지 않는다. [접수 서비스](../src/main/java/com/catchtable/waiting/service/WaitingIntakeService.java) · [저장소](../src/main/java/com/catchtable/waiting/repository/WaitingReceiptRepository.java)
- 신규 유효성과 접수일은 매장 잠금을 얻은 뒤 한 번 읽은 서울 시각으로 판정한다. ON 힌트를 읽고 공유 잠금을 기다리다 자정이 지나면 쓰기 없는 첫 TX를 끝내 잠금을 반환하고 새 날의 경로를 배타 잠금 아래 다시 고른다. 이미 수락된 키는 자정 후에도 원래 표를 조회한다.
- 이번 구현은 큐 Redis가 없어도 동작하는 PG 접수 경로다. 등록·취소 소비자, Redis 승격·AOF 복구, 매장 확대/드레인·복귀 자동화, 예약 캐시와 프런트 폴링은 후속 단계다. 이번 호출·설정 변경은 격리 DB에 한정했다.

## 검증 조건

기준선과 분리한 루프백 PostgreSQL 16.15와 앱 1·3대로 실행했다. 합성 A매장은 장부, B매장은 레거시 등록과 가용 조회를 사용한다. 앱 합계 3 CPU·heap 768 MiB·풀 12개, DB 2 CPU/768 MiB, 동일 Hikari 5초·클라이언트 12초 제한이다. 성공 고객만의 분위수, 창 내 실제 호출/전송, 반환 표와 PG 행의 일치, 다른 매장의 오류·회복을 따로 집계했다. 목표 후보는 대표 입력 전원 커밋·응답, 접수 p95 1초·p99 2초다. 확정 운영 SLO는 아직 없다.

최초 구현은 순번·대기표 쓰기와 최초 키 저장 사이에 앱–DB 왕복 1회가 더 있었다. 5천 명/10초의 첫 회차에서 발급 SQL 호출 5,000회에 누적 실행 53.2초, 차단 세션 표본 45개가 모두 그 문장이었다. 이에 최초 키 바인딩을 동일 SQL에 포함했다. 예비 JAR와 원시 자료는 별도로 보존했다. 두 JAR의 회차를 합산하지 않는다.

## 기능 검증과 적용 경계

- 같은 POST에서 202를 기대한 테스트가 이전 구현의 201을 받아 실패하는 것을 먼저 확인했다. 키 없는 서비스 호출의 직접 등록, 이미 등록한 날의 장부 개설, 매장 잠금을 기다리는 동안 서울 자정이 지난 경우도 각각 고치기 전 실패를 확인했다.
- 전용 DB `rb0_tests`에서 Java 21 `./gradlew --offline --max-workers=2 build`를 실행했다. 마지막 제품 소스 기준 109개 테스트 클래스, **1,217건 통과**, 실패·오류·건너뜀 0이다. GET 소유권, 별칭 키, 마감 후 재시도, 인원 충돌, 존재하지 않는 회원, 영업시간, 한도, 롤백, 동시 신청과 자정 경계를 포함한다.
- 실 HTTP 스모크에서 앱 1이 반환한 202를 프록시가 클라이언트에게 전송하지 않고 연결을 종료했다. 클라이언트는 RemoteDisconnected를 받았다. 앱 2에서 같은 키로 받은 200은 앱 1의 표 ID·순번·경로와 같았다. 앱 3의 다른 키도 원래 표로 연결됐다. 다른 매장에서 두 앱이 마지막 한 자리에 동시에 요청했을 때 한 요청은 202, 다른 요청은 재시도 안내가 있는 429였다.
- 수락 순번은 같은 매장·접수일마다 PG에서 유일하다. 후속 요청이 시작되기 전에 응답까지 끝난 선행 신청이 있다면 그 순번보다 큰지도 원시 시각과 PG 행으로 검사한다. 서로 겹쳐 들어온 요청의 클릭 순서나 아직 없는 식당 번호 발급 워커의 순서를 이 검사로 증명할 수 없다.
- 측정 중 제품 JAR의 SHA와 소스를 고정했다. 실험 DB를 만든 기준선 JAR의 해시는 초기화 메타데이터에, 실제 HTTP 요청을 받은 JAR의 해시는 각 회차 config.json에 있다. 업무 경로가 달라졌으므로 기존 201 번호 발급 시간과 새 202 대기표 시간을 합쳐 개선율을 계산하지 않았다.
- 현재 상태 조회는 커밋된 표의 PENDING을 읽는다. 전용 표의 보관 기간, 별칭 키 정리, 최종 번호와 취소 상태의 연결은 후속 설계 대상이다. 수용량은 그날의 미완료 고객 수를 센다. 모든 앱이 새 코드를 사용하는 격리 배치에서만 이번 경로를 열었다. 구버전 바이너리가 섞인 배포와 운영 전환은 검증하지 않았다.

## 대표 오픈에서 관측한 병목

최종 앱 3대의 고정 1초 창에서 3회 각각 10,000건을 실제로 호출하고 소켓에 썼다. PG는 10,000·9,778·9,431건을 커밋했지만 12초 안에 본인이 대기표를 받은 고객은 7,430·5,469·5,824명이었다. 2초 안에 받은 고객은 488·435·455명이었다. PG 커밋 후 첫 202가 없던 고객과 PG에 첫 기록이 없는 고객을 따로 센다.

같은 세 회차에서 전체 앱의 Hikari 대기 표본 피크 합계는 105·109·103개, Hikari 연결 취득 타임아웃 카운터 증가는 모두 0이었다. 즉 클라이언트 12초 타임아웃을 Hikari의 5초 취득 실패로 환산할 수 없다. 차단된 세션의 현재 SQL 중 일자별 순번 발급 문장은 67·60·54개 표본에서 보였다. 해당 SQL 누적 실행시간은 61.50·75.55·60.84초다. 이는 동시 세션의 PG 실행시간 합계로, 회복 벽시계 시간과 구분한다.

B매장의 오류는 같은 세 회차에서 3·20·14건이었다. B의 조회·등록이 모두 성공하고 p95가 직전 4초의 2배 이내인 상태로 연속 두 개 4초 구간을 채운 시각은 A 폭주 종료 후 24·32·32초였다. 20초 후보를 넘었다. 1초 본 구간의 B 표본은 매초 조회 9·등록 3건이므로 운영 SLO를 정하기에는 작다.

동일한 5천 명/10초 조건에서 새 키를 저장하는 별도 INSERT 호출은 회차당 5,000번에서 0번으로 줄었다. 일자별 발급문 누적 실행시간은 초기 53.2·55.1·52.8초, 최종 46.3·43.9·31.8초였다. 반면 고객 202 p95는 초기 1.88·2.22·2.01초, 최종 2.02·2.91·1.93초였다. DB 왕복 제거는 확인했지만 고객 p95의 일관된 개선은 확인하지 못했다. 두 빌드 사이에는 잠금 이후 시각 재판정 보완도 들어갔고, 호스트는 공유 상태였다.

후속 판단에서는 단건 수락 TX의 앞부분(회원·신청키·영업 유효성 조회)과 매장·일자 행 직렬화, HTTP 입구와 B업무의 자원 경쟁을 구분해야 한다. 단건 경로를 유지하며 접수/기타 업무의 예산을 분리하는 방법은 B매장 보호를 단독으로 검증하기 좋다. 짧은 일괄 커밋은 같은 매장의 커밋 횟수를 줄일 수 있지만 세 앱이 수락 순서를 합치는 기준, 커밋 전 앱 종료·일부 유효하지 않은 요청·재시도 취급을 먼저 설계해야 한다. 고객에게 성공을 돌려주는 시점은 두 안 모두 PG 커밋 후여야 한다. 실제 운영 상한이나 마이크로배치 크기는 결정하지 않았다.

## 응답 유실분을 재기동한 다른 앱에서 복원
