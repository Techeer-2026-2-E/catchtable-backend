## 검증할 질문

같은 매장에 1만 명이 1초에 몰릴 때, 한 트랜잭션에 여러 접수 행을 넣으면 고객이 첫 PENDING 대기표를 더 빨리 받는가? B매장의 평상시 조회와 웨이팅 등록도 빨리 회복하는가? 이전 앱 3대 대표 시험의 성공 응답을 요청 ID로 맞추면 클라이언트 쓰기 완료→Tomcat access-log 시작 p95가 11.23·11.38·11.22초, 로그 시작→종료 p95는 0.47·0.55·0.52초였다. 시간은 서로 다른 호스트/VM 시계에서 얻은 추정 구간이며, 앞 구간을 하나의 특정 내부 큐 대기로 단정할 수 없다.

## 후보 구현

- 기본값은 단건이다. 실험 설정 `waiting.intake.batch.enabled=true`에서 유효한 요청 키가 있는 POST를 앱 내 매장별로 모은다. 장부 대상 매장·서울 접수일 선택은 기존 PG 설정이 담당한다. B매장과 키 없는 호출의 201/200/409 계약은 유지한다. 수집 중에는 DB 연결을 얻지 않는다. 각 묶음의 첫 HTTP 요청 스레드가 쓰기를 담당하고 다른 요청은 결과를 기다린다. HTTP 처리 스레드 수와 풀 크기는 모든 비교군이 같다.
- 수락 순서는 PG가 매장·접수일 카운터를 갱신해 트랜잭션을 커밋하는 순서다. 묶음 안에서는 앱에 등록된 요청 순서대로 유효한 신규 신청에 연속 순번을 준다. 서로 다른 앱에서 겹쳐 도착한 두 묶음은 같은 PG 행에서 순서를 정한다. 프로세스 메모리에 들어간 신청에는 접수 성공을 응답하지 않는다.
- 일괄 TX는 회원을 ID순으로 잠근 뒤 회원별 키·활성 표·기존 등록을 일괄 조회하고, 매장 잠금 뒤 같은 서울 시각으로 영업 여부를 판정한다. 자정에 힌트가 바뀌면 기존 단건 경로가 새 TX에서 라우팅을 재확인한다. 같은 키·같은 본문, 새 별칭 키, 인원 충돌, 없는 회원, 수용 한도 초과를 요청별로 처리한다. 묶음 전체의 공간이 부족해도 남은 자리만큼 앞의 유효 신청을 먼저 수락한다.
- PG 행 잠금 아래에서 새 표·최초 키·카운터를 집합 SQL로 기록한다. 별칭도 같은 TX에 기록한다. Spring이 커밋 성공을 반환할 때까지 각 요청의 결과를 공개하지 않는다. 잡고 있는 외부 Spring 트랜잭션이 있는 호출은 기존 전파·롤백 의미를 유지한다. 스키마는 단건 경로의 V41·V42를 그대로 사용한다.

## 시험 구성

`direct`는 기존 단건, `group1`은 새 코드에 묶음 크기 1·수집 지연 0ms를 적용한 대조군, `batch32`는 최대 32건과 수집 지연 후보 2ms다. 운영 설정은 결정하지 않았다. 같은 JAR·fixture·루프백 PG16·CPU·heap·풀 예산에서 번갈아 실행한다. 앱 합계 3 CPU·heap 768 MiB·Hikari 12·Tomcat 스레드 120, PG 2 CPU/768 MiB, 클라이언트 제한 12초다. 앱 3대에서 A매장 1천·5천·1만 명/10초, 대표 1만 명/1초를 시험하고 1대에서도 대표 조건을 반복한다. B는 매초 날짜별 조회 9건·레거시 등록 3건을 보낸다. 대표 1초 창의 처음 990ms에 신청을 배분한다. 각 회차는 새 DB와 JVM에서 시작한다.

HTTP 202의 PG 표·키·순번을 대조하고 초기 키와 대기표의 삽입 트랜잭션 ID(`xmin`)도 비교한다. 수용량 초과를 제외한 정상 신규 입력에서 서로 다른 `xmin` 개수가 실제 접수 커밋 수다. 다른 앱에서 앞 응답이 끝난 뒤 시작한 신청의 순서 위반, 중복·누락, B매장 오류와 회복, 성공 응답별 시간 구간과 호스트·풀·잠금 시계열을 함께 기록한다. 근거는 회차별 client.jsonl, Tomcat access 로그, receipts/keys/waiting.csv, pool·statements·observations 파일이다. 202는 첫 접수 대기표다. 이번 후보에는 식당 번호 발급·취소 소비자, Redis 전환, 프런트 구현이 없다.


## MacBook 준비와 Mac mini 인계

MacBook의 예비 32건 묶음에서는 후속 묶음의 선두가 선행 TX를 기다리는 동안 2ms 경과만으로 그룹이 분할됐다. 첫 대표 시험에서 PG에 저장된 1만 건이 4,210개 TX(평균 2.375건)였다. 선행 TX를 막고 2ms를 넘겨 간격을 둔 요청 5개를 추가한 테스트에서 이전 코드는 1건 그룹 6개를 만들었다. 수정 후 첫 1건·다음 5건으로 커밋하도록 검증했다. 선행 그룹이 비어야 하는 동안에는 최대 크기까지 계속 모으고, 앞 TX가 끝나면 남은 수집 시간만 기다린다. 클라이언트 응답 방식, Tomcat 연결·스레드 예산, PG 커밋 후 수락 원칙은 그대로다.

같은 회원·서로 다른 키, 같은 키·다른 본문, 없는 회원, 여유보다 많은 신규 요청, 이미 마감된 매장의 재시도를 한 TX에서 검증했다. 오름차순 회원 락으로 순서가 반대인 두 동시 묶음이 원래 고객당 한 표만 남기는 것도 확인했다. 실제 PG의 지연 가능한 트리거로 COMMIT을 막고 두 HTTP 응답이 아직 오지 않았음을 관측한 뒤 실패를 주입했다. 두 요청 모두 성공 응답을 받지 않았고 표·키·카운터가 롤백됐다. [HTTP 회귀 테스트](../src/test/java/com/catchtable/waiting/controller/WaitingBatchHttpTest.java) · [수집 대기 회귀 테스트](../src/test/java/com/catchtable/waiting/service/WaitingIntakeBatcherTest.java)

사용자가 이동을 위해 개인 Mac mini로 측정을 옮겼다. MacBook에서 완료한 예비 회차 및 최종 JAR의 스모크·장애 주입·초기 부하는 그 장비의 원본으로만 보존한다. 새 회차 시작을 막은 뒤 MacBook 전용 PG를 중지했다. 두 호스트의 측정값을 하나의 캠페인으로 합치지 않았다.

Mac mini는 Darwin arm64, 10코어, 32GiB이며 Docker Desktop을 시작해 독립 실행했다. 시스템 전체 Go 설치가 없어 MacBook에서 빌드한 같은 Darwin arm64 발생기 바이너리를 사용했다. 정확한 제품 JAR, 소스 검증용 src/main 스냅샷, 합성 fixture와 계측 스크립트, 로컬의 Linux arm64 이미지 두 개를 전용 SSH 실험 폴더로 전송했다. PG 비밀번호는 각 호스트에서 별도로 생성했다. Docker 이미지 단일 플랫폼 export/load 후 manifest ID는 달랐고 두 이미지의 루트 파일시스템 레이어 목록·컨테이너 실행 설정·아키텍처가 원본과 일치했다. 외부 레지스트리나 Git 서버에 게시하지 않았다. JAR·파일 SHA 검증, 앱·부하 발생기·PG·원시 기록을 모두 Mac mini에서 수행했다.

### 자동 실행이 멈춘 이력과 복구

로컬 시각 19:18, 전체 33회 중 23번째 회차(앱 3대, 1천 명/10초, 최대 32건) 직후 실행기가 중지됐다. 신규 1,000건이 전부 성공했고 PG 삽입 TX도 1,000개, 독립 앱 계측값도 1,000이었다. 3개 앱에 균등 배분한 요청이 2ms 안에 겹치지 않은 정상 결과였다. 진단기가 목표 인원 수만 보고 최대 묶음 크기가 반드시 1보다 커야 한다고 잘못 요구했다. 중지 기록·초기 판정 JSON을 보존했고 20:01에 재개했다. 약 43분간 새 부하를 실행하지 않았다.

진단기는 이제 측정값의 일치(PG 트랜잭션 ID와 앱 계측 건수, 최대 허용 크기, 최초 키·표의 동일 TX)와 실제 다건 묶음 발생 여부를 각각 기록한다. 고객 지연·입력 창·전원 응답·B매장 회복 기준은 바꾸지 않았다. 기존 회차 23개의 순서·JAR·원본을 재확인한 뒤 같은 DB 컨테이너와 fixture에서 나머지 회차만 재개했다. DB는 각 회차 독립 복제본이다.

MacBook 수집 로직 보완 전에는 대표 오픈 단건 1회(최초 202 6,617/PG 9,849), group1 1회(7,349/10,000), batch32 2회(9,488·9,515/각 10,000)를 보존했다. 예비 batch32의 접수 p95는 11.69·11.75초였다. 수정 후 호스트 전환 직전 단건 1회는 7,311/10,000·p95 11.62초, batch32 1회는 10,000/10,000·p95 5.40초·실제 450 TX였다. 초기 JAR 및 원시 자료는 로컬 `build/intake-lab/formation-pilot/`, 수정 후 실측은 `build/intake-lab/raw/`에 있다. 이 작은 예비 표본을 Mac mini의 반복 횟수에 더하지 않았다.

전체 검증은 MacBook의 전용 `rb0_tests`에서 `./gradlew --offline --max-workers=2 build`로 실행했다. 최종 빌드는 112개 클래스, 1,228개 테스트, 실패·오류·건너뜀 0이었다. Mac mini에서는 같은 JAR의 SHA와 모든 시험 입력 파일을 확인하고 실제 HTTP를 실행했다. 원격 호스팅 CI와 운영 배포는 이번 범위에 포함하지 않았다. [재현 방법](../tools/waiting-intake-benchmark/batch-comparison.md)

## Mac mini 대표 오픈 결과

앱 3대, 매 회차 목표 1만 건/고정 1초에서 batch32는 모두 10,000건을 같은 창에 소켓 전송하고, 10,000행을 PG에 저장했으며 10,000명이 12초 안에 대기표를 받았다. 실측 426·427·428개 PG 트랜잭션으로 평균 23.47·23.42·23.36건씩 커밋했다. 건별 direct는 첫 202 4,211·4,153·3,970건이었다. direct 첫 회차는 1초 창 내 전송이 9,977건이라 만 건 입력 검증에 불충분했고 나머지 두 회차는 입력을 채웠다.

- batch32에서 첫 202 p95는 5.08·5.20·5.39초, p99는 5.74·6.22·6.03초였다. 2초 이내 받은 고객은 2,562·2,476·2,441명이다. 동일 처리 경로를 1건씩 커밋한 group1은 5,279·5,925·5,926명이 첫 202를 받았고 성공 p95가 11.46~11.65초였다. 묶음이 없는 대조군까지 확인했지만 개별 최적화의 효과를 독립적인 백분율로 계산하지 않았다.
- direct의 B 오류는 45·43·51건, 회복은 각 32초였다. batch32에서 오류는 세 번 모두 0, 회복 후보 시각은 각 16초였다. **폭주 중 B가 평상시 응답속도를 유지한 것은 아니다.** batch32 B조회 p95는 직전 18~22ms(n=36)에서 폭주 중 4.91·6.24·5.92초(n=9), B등록도 4.53~4.82초(n=3)였다. 작은 표본의 p95는 최대값에 가깝다.
- batch32에서 1초 간격 Hikari 대기 합계의 관측 피크는 각 0, direct는 106~108이었다. 순간적인 대기를 배제할 수 없다. 동일 ID의 성공 202들에서 전송 완료→Tomcat 로그 시작 p95는 batch32 5.04~5.31초, Tomcat 로그 시작→종료는 0.181~0.186초였다. 기록 경계에 Docker 포트 전달·연결·서버 처리 대기가 함께 들어 있으므로 남은 수 초를 특정 큐 하나의 시간으로 쓰지 않는다.

## 커밋 경계에서 앱 1대 종료

새 격리 DB 2개에서 A매장 신청 2개를 동일 배치로 묶고, PG 수락 전에는 둘 다 응답하지 않은 상태를 확인했다. 같은 앱의 다른 B매장 등록은 두 경우 모두 201을 반환했다. 소유 라벨·컨테이너 ID·DB를 확인한 A 처리 JVM 1개만 강제 종료했다.

| 종료 시점 | 앱 종료 직후 PG | 다른 앱에서 재시도 | 최종 상태 |
| --- | --- | --- | --- |
| 일자별 행을 잠그기 전 DB에서 차단 | 표·키·순번 차감 모두 0 | 202·202로 신규 수락 | 같은 TX에서 두 표, 순번 1·2, 미완료 2 |
| 실제 PG COMMIT 시점의 지연 트리거에서 차단 | 첫 연결은 모두 끊겼고, 차단 해제 뒤 이 실행의 PG에는 두 건이 함께 커밋됨 | 200·200으로 원래 표·순번 | 키·표·카운터가 재시도 전후 동일 |

COMMIT 중 앱 종료의 결과는 DB에서 재조회해야 한다. 이 회차의 두 건 커밋을 모든 장애의 보장으로 일반화하지 않는다. 별도 프로세스/HTTP 스모크에서는 upstream 202 후 응답 연결을 끊었을 때 다른 앱의 동일 키 및 별칭 키로 같은 표를 복원했고, 두 앱이 마지막 슬롯에 경합하면 202·429 한 건씩이었다. 자동 재시도 실험은 자연 발생한 ‘PG에 행이 있으나 첫 202가 없는’ 집합만 대상으로 삼는다.
