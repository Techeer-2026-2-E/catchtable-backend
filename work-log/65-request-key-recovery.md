# 기능10 — 저장된 승인 요청 키로 결과 불명 복구

## 문제와 범위

[기능10 #65](https://github.com/Techeer-2026-2-E/catchtable-backend/issues/65)의 응답 유실 복구를 현재 `dev@a3ce022`와 대조했다. 승인 성공 응답을 받기 전에는 결제 행의 `payment_key`가 비어 있지만, 예약에는 외부 호출 전 `beginPaymentApproval`로 같은 요청의 키가 이미 저장된다. 기존 재확인은 결제 행의 키만 사용해 이 경우 orderId 조회로 내려갔다. [gsk는 orderId 조회를 지원하지 않으므로](https://docs.tosspayments.com/reference#orderid로-결제-조회) 정상 예약의 응답 유실도 TIMEOUT에 머물 수 있었다.

이 보완은 예약금 흐름에 필요한 공통 재확인의 조회 키 선택만 바꾼다. sync·자동 재확인·웹훅 호출부와 기존 승인·정산·환불 보호를 함께 확인했다. 결제 상태·API 요청/응답·키 종류·스키마·예약 기한을 새로 정의하지 않는다.

## 변경

- 결제 행에 키가 있으면 기존 키를 우선한다.
- 키가 없으면 예약에 사전 저장한 승인 요청 키를 확인한다. 기존 `matchesPaymentApproval`로 결제 ID·주문번호가 같은 요청임을 확인하고 비어 있지 않은 키만 조회에 사용한다.
- 같은 원본을 확인할 수 없으면 기존 orderId 조회를 유지한다. 이 경로는 여전히 API 개별 연동 sk 키가 필요하다. 다른 요청의 키를 빌리거나 결과를 임의로 성공/실패 처리하지 않는다.
- 외부 조회는 기존 트랜잭션 밖에서 수행하고, 결과의 주문·금액·원본 검증과 기존 정산 처리를 유지한다.

## 검증 — 2026-11-04

실제 매장 설정 API부터 시작하는 `StoreDepositPaymentFlowTest`에서 승인 응답 유실과 gsk의 orderId 조회 거절을 재현했다. 변경 전 5개 중 해당 1개가 `DONE` 대신 `TIMEOUT`으로 실패했다. 변경 후 5개 모두 통과하며 저장된 키 조회 1회·추가 승인 없음·원래 기한 뒤 같은 슬롯 보호를 확인했다. 다른 주문의 승인 기록은 키를 공급하지 못하는 부정 사례도 포함한다.

첫 전체 실행에서는 861개 중 기존 8개가 이전 조회 메서드로 목을 지정하거나 요청 키 없이 조회 fixture를 등록해 실패했다. 같은 승인 요청 키로 조회하도록 목·fixture를 맞췄으며, 잠금 밖 조회·동시 만료·종료 예약 보존·최초 기한의 반환·재승인 없음에 대한 단언은 유지했다. 원본 없는 결제의 orderId 조회 검증도 남겼다.

최종 `./gradlew clean build --no-daemon`은 새 일회용 PostgreSQL16, `127.0.0.1:60380`, DB `ct_request_key_test`, 빈 Toss 키와 loopback PG 주소에서 **81클래스 861개·실패/오류/건너뜀0**, bootJar 성공이다. 기존 마이그레이션 30개의 해시가 동일하다. red·green·최초 전체 실패·수정 후 전체 로그와 JUnit XML·명령·JAR 해시를 별도 로컬 산출물에 보존했다. 컨테이너는 tmpfs와 종료 시 자동 삭제로 만들었고 검증 후 제거했다.

## 확인 범위

기존 [PR #238의 실제 PG 독립 검증](2026-11-03-toss-independent-validation.md)은 승인·취소·paymentKey 조회를 이미 확인했다. 이번 회귀는 실제 PG 호출 없이 그 조회 능력에 맞춘 예약 원본 연결을 검증한다. 새 카드 인증이나 결제는 다시 실행하지 않았다. 실제 설정→서비스 앱→Toss의 단일 전체 실행, 제품 프런트·공유 DB 적용·배포 확인과는 구분한다. 새 소스 PR의 CI·리뷰·머지를 확인한 뒤 백엔드 완료 상태를 반영한다.
