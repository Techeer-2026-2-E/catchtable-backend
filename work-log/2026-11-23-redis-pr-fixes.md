# Redis PR 성능 및 검토 후속

PR #297의 첫 검토 커밋은 `651b8a5d18d48dd197fa2241c37cbac47ed0b1cc`다. 대표 오픈과 회복 기준을 충족하기 전에 리뷰 상태로 전환했던 일을 바로잡아 PR을 초안으로 되돌렸다. 이 기록에서는 이전 실패 원본을 보존하고, 같은 고객 수·1초 입력·PG 커밋 후 응답·식당 번호·다른 매장 조건으로 변경을 검토한다. 프론트 소스는 범위 밖이다. [첫 검증 원본](2026-11-22-redis-product.md#v49-후속-검증)

## 관측한 병목

- V49의 앱 3대 대표 오픈 세 회차에서 소켓 쓰기→Tomcat 처리 시작 p95는 각각 약 11.20·7.98·9.80초였다. 1차 회차에는 10,332번의 매장 잠금 조회, 워커가 사용하지 않는 앞 팀 수 계산 10,332회, 장부 상태 조회 45,649회가 기록됐다.
- 저장을 수행하지 않는 별도 Actuator 전송 진단(제품 성능 판정에서 제외)에서 Docker Desktop 공개 포트의 p95는 2.34초, 같은 앱의 Linux 브리지 경로는 0.31초였다. 이후에는 전용 Linux 앱 VM 밖의 별도 3 CPU 고객 발생기 VM에서 실제 HTTP로 접근하는 경로를 사용했다. 비교에는 실제 최초 소켓 쓰기 시각을 포함한다. 네트워크와 JVM 설정 변경 효과를 코드 단독 효과로 쓰지 않는다.
- Mac mini의 앱·PG는 하나의 격리 Linux VM, Redis 캐시·대기열 주·복제는 별도 커널 VM, 고객 발생기는 별도 VM에 배치했다. 앱 합산 3 CPU·heap 768MiB·Hikari 12개, PG 2 CPU·768MiB를 유지했다. 서비스 VM에서 세 Redis VM으로는 사설 가상망으로 연결한다. 기존 두 물리 장비 사이의 SSH 경로는 이전 결과로 남겨 두었다.

## 구현과 반례

- 번호를 발급할 때 매장·날짜 선두를 제한된 묶음으로 권한 위임하고, 토큰과 선두를 재확인한 뒤 한 트랜잭션에서 식당 행·기존 이벤트·장부 연결을 기록한다. 한 매장의 번호 순서는 기존 PG 레인 잠금이 직렬화한다. 설정 전환·점주 순서 변경과 충돌하는 매장 공유 잠금은 유지한다. 워커에서 사용하지 않는 앞 팀 수 계산을 없앴다. 취소 요청이 섞인 묶음과 오래된 처리 토큰을 별도로 검사한다.
- V52는 미완료 표에서 실제 활성 웨이팅으로 이어지는 회원·매장·날짜 고유 제약을 추가했다. 일반 신규 묶음은 중복 선조회 없이 장부·키를 한 번에 추가한다. 활성 신청이나 기존 키가 하나라도 있으면 서브트랜잭션을 되돌리고 기존 분류기로 각 고객의 200·409·429·신규 수락을 판정한다. 고유키와 실제 외래키는 유지한다. 측정 시 빈 장부에서 성장한 테이블의 FK 검사 1만 회가 69만 개 이상의 공유 버퍼 블록을 읽는 경우가 있었다.
- V50·V51은 같은 매장의 무효화 기록을 잠기지 않은 행에 합치려고 했다. 순차·반대 순서 테스트는 통과했지만, 실제 PG 연결 4개·커밋 6,000건에서는 물리 행 위치로 갱신 대상을 찾던 방식이 2,979행을 남겼다. V55는 트랜잭션당 advisory lock 하나로 논리 슬롯을 고르고 `(store_id, mailbox_slot)`에 upsert한다. 같은 시험에서 남은 것은 4행이었다. 한 행은 최대 32개의 개별 날짜를 보관하고 그 이상은 해당 매장 전체를 무효화한다. 기존 드레이너도 매장 전체 표식을 읽을 수 있다.
- 고부하 접수에서는 매장별 대기 목록과 전용 커밋 작업자를 사용한다. Tomcat은 서블릿 요청을 만들기 전에 소켓 작업을 큐에 두고, 동시에 처리할 가상 작업자 수를 힙 크기와 설정값으로 제한한다. 원래 Spring MVC 매핑·회원 확인·검증·예외 처리에서 요청을 받아 PG 커밋 뒤 응답한다. 별도 게이트웨이 배포나 프론트 변경은 없다.
- 이전 JAR을 무스왑 Linux cgroup의 같은 제한에서 실행했을 때 JVM 세 대가 cgroup OOM으로 종료된 회차가 있었다. 중간 구현에서도 완료된 비동기 HTTP 교환을 제때 반환하지 못해 Java 힙이 고갈된 회차를 보관했다. 코드 캐시·직접 메모리·스택과 소켓 버퍼를 따로 제한하고, 커밋 후 응답을 같은 Tomcat 큐에 재접수하는 경로를 제거했다. 불충분한 입력·실패를 정상 회차에 합산하지 않는다.

## 실제 영업 시작과 검증 도구

- V53은 일반 영업시간·활성 일자·중복 없는 신청을 한 SQL 호출에서 검증한다. 특별 영업일, 휴무, 브레이크, 자정 경합, 부분 수락, 기존 키와 활성 회원은 원래 분류기가 처리한다. V54는 한국 시각의 실제 개점 시각도 포함하고, 전날 활성화한 매장의 첫 유효 신청이 당일 장부를 만들게 했다. 영업 전 거절된 한 건만으로 빈 일자 행이 생겼던 반례를 고쳤다.
- 오픈 회차마다 전날부터의 매장 정책을 준비하고 실제 DB 시간으로 다음 영업 시작 분을 예약한다. 개점 전 같은 API의 409와 당일 장부 0개를 확인한 뒤 그 영업 시작 초에 1만 건을 전송한다. 최초 소켓 쓰기와 가장 이른 PG 접수 시각을 개점 시각에 대조한다.
- Docker Desktop 공개 포트와 직접 가상망은 다른 전송 경로다. 고객별 동일 HTTP API·최초 키·커밋 내구성·선착순·타임아웃·정합성 대조를 유지했다. 일반 요청과 최초 접수는 동일한 공개 포트로 들어간다. 앱 1대·3대 모두 합산 HTTP 연결 상한 12,000개, accept backlog 약 4,096개, Java heap 768MiB·3 CPU·Hikari 연결 12개다.
- SQL 대기 재현기는 statement timeout과 프로세스 종료를 구분해 처리한다. 0.35초 제한에서 0.424초에 복귀하고 남은 DB 세션은 0개였다. 수집기 종료·부분 생성 자원 복원, 오래된 JAR·혼합 비교·OOM이 있는 회차 재개, 입력 부족·빈 보고를 검사한다. TTL 시험은 실제 3개 적중, 미스 병합은 3개 DB 계산·9개 합류, 늦은 계산은 원래 버전의 실제 저장값을 확인해야 통과한다.

### 장애와 근거 보관

- 서로 다른 Linux 커널의 Redis VM 세 대 중 주 노드 VM을 강제 종료했다. 두 Sentinel의 합의 및 승격은 3.866초, 접수된 두 고객의 실제 2·3번 확인은 4.037초에 관측했다. 이전 주 노드는 새 부팅 ID로 복제에 복귀했다. 캐시 VM 종료 중에도 DB 우회와 4번 발급을 확인했다.
- 기본 Sentinel 이름, 응답하지 않는 첫 Sentinel 이후의 정상 시드, Redis 프로세스 동시 종료·AOF 복원, 처리 중 취소 및 PG 중단 503·동일 키 재시도를 별도로 재현했다. 캐시의 정상/장애 동일 키 12요청은 앱 3대에서 각각 대표 계산 3건·합류 9건이었다.
- 힙 또는 컨테이너 메모리 문제를 만났던 초기 진단 DB 2개의 복구 가능한 사본을 만들었다. 이미 수락한 16,634건을 모두 원래 키·표·번호로 재조회했다. 최초 실패한 회차의 결과는 그대로 보존했다.
- 운영 서버의 최소 메모리 계획은 4GB다. Mac mini에서는 앱과 PostgreSQL을 5GiB Linux VM 안의 서로 다른 cgroup에 뒀다. 앱 3대의 합산 메모리 상한은 1,920MiB(그중 Java 최대 힙 768MiB), PG 상한은 768MiB다. 대표 오픈 세 회의 같은 시점 Docker working set을 합산한 최고치는 각각 1,765.4 · 1,764.6 · 1,777.8MiB였다. 여기에는 OS와 별도 VM의 Redis·고객 발생기 메모리가 포함되지 않는다. 실제 운영 장비와 물리 호스트 장애 격리는 별도 검증 범위다.
- Mac mini 원시 표본·DB 결과 등 626개 파일의 보관 묶음 SHA-256은 `de66c80d2f45286fc29c65094f8dd274d4ca468b28f7fce628e50e8f945f08d0`이다. 사본을 다시 읽어 파일별 해시를 확인하고 전용 VM 다섯 대와 실험 PostgreSQL을 종료했다.
