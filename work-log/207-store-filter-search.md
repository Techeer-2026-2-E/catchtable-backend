# 대량 매장 필터 검색 수정 복구 — #207

2026-10-29. [기능2](https://app.notion.com/p/3d548d76fa328167bcfadfb92c124e48), 선행 [PR200](https://github.com/Techeer-2026-2-E/catchtable-backend/pull/200). 최신 dev 기준 `dd9d96dd866d96db34be15ecd3618909e99b52a0`.

## 왜 남았고 무엇을 복구했나

PR155 로컬 검토에는 전체 매장 ID를 IN에 넣는 필터의 대량 실패를 고친 코드가 커밋 없이 남아 있었다. 이후 PR200이 무필터 페이징과 객체 응답을 머지했지만 필터의 전체 조회는 후속으로 남겼다. 이전 로컬 초안의 배열/X-Has-Next·기본20/최대100 계약은 이식하지 않았다.

무필터 DB Slice는 유지한다. 인원·날짜 필터는 카테고리·ACTIVE 테이블 EXISTS·예약 창/마감·이용시간 전체의 영업/브레이크 조건을 DB에서 먼저 적용하고 id 순으로 size+1개만 읽는다. 현재 `stores/page/size/hasNext`, 기본0/10·최대50과 입력 검증은 유지한다. 긴 페이지의 offset은 long으로 SQL에 바인딩해 기존 필터 경로의 정수 오버플로를 피한다. 점주 없는 매장은 기존 V22의 검색·지도 전용 정책에 따라 예약 조건 필터에서 제외한다.

## 검증

Java21.0.12.1, 전용 PostgreSQL16 빈 최종 DB `audit_search_final`, 기본 연결 한도100. 합성 데이터만 사용했다.

- `StoreSearchControllerTest` 5개: 최초3개 실패 중1개는 JDBC 업데이트 후 남은 테스트 영속성 캐시였다. 테스트만 clear한 재현 실행은 2개 실패로, 66,000건 인원 필터500과 잘못 남은 공공 매장 테이블의 결과 포함을 재현했다.
- 변경 후5개 통과. 인원/날짜 단독·복합 필터, 중복 테이블, 카테고리·페이지/정렬/hasNext, 기본10/최대50, 자정/브레이크·마감/예약 창·삭제된 시간, 큰 long offset을 확인했다.
- 최종 `./gradlew clean build --no-daemon --console=plain`: 55 classes / 484 tests; failures/errors/skipped 0; bootJar success.
- 이전 두 기능의 전체 빌드에서 병렬 실행의 연결 고갈을 확인해 이 최종 빌드도 새 빈 DB에서 직렬 실행했다. 별도 feature 수정과 검증 결과를 합산하지 않는다.
- 기존6곳 원본과 마이그레이션을 보존했다. 전체 운영 데이터·실제 프런트·배포 성능 검증은 하지 않았다.

## 남은 점

일반 dev PR·미머지이며 기능2 문서 #210은 별도다. offset 페이징의 깊은 페이지 비용은 남는다. 검색은 조건에 맞는 매장을 고르며 실제 테이블 재고의 최종 배정은 예약 생성에서 확인한다. 다른 기능 PR이나 운영 DB를 변경하지 않았다.
