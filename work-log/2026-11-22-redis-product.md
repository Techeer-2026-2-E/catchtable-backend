## 문제와 구현

오픈 시점에 첫 HTTP 응답이 끊기면 고객은 번호가 발급됐는지 알 수 없었다. 접수 장부에 먼저 기록하고 기존 요청 키로 결과를 복구하도록 했다. 수락 순서는 PostgreSQL의 매장·서울 접수일 행에서 정한다. Redis에는 처리할 매장·날짜를 게시한다. PG 커밋만 성공한 경우, Redis 게시만 남은 경우, 앱 응답만 유실된 경우를 각각 장부에서 대조할 수 있다.

- V41~V43은 접수표·최초 키와 별칭·수락 순번·처리 상태·취소 의사를 보관한다. 즉시 발급은 201, 미완료 수락은 202, 동일 신청 확인은 200이다. 번호가 생기기 전에는 실제 식당 번호를 내려주지 않는다. 여러 앱의 워커는 같은 매장의 선두를 확인하고, 중단 후 처리 권한을 다시 받을 때 옛 워커의 쓰기를 차단한다.
- V46·V48은 수락한 표와 실제 번호 연결, 원복 전 취소·순서, 신규 경로와 기존 경로가 공유하는 PG 등록 허가를 확인한다. 번호 발급은 기존 웨이팅 서비스·SSE 기록을 사용한다. 대기열 Redis 장애 때에도 PG 장부 여유 안에서 새 신청을 받고, 취소·조회·재시도와 복구 뒤 번호 발급을 지원한다.
- V44·V45·V47은 예약과 무효화 기록을 같은 트랜잭션에 쓴다. 커밋 후 Redis에서 날짜·매장 버전을 교체한다. 가장 늦은 옛 계산도 읽기 시작 시점의 키에만 기록한다. 일반 JSON의 최대 수명은 2초다. 서울 자정·예약 마감·선점 만료를 반영하고, 장애 시 DB 우회에는 앱별 고정 허가와 동일 요청 병합을 적용한다.
- 로컬 도구는 합성 회원으로 HTTP 응답, PG 장부·취소, 실제 식당 번호를 대조한다. 매장별 다음 날 확대·같은 요청 재실행·원복·판정 미달 시 중단을 코드로 처리한다. 기능 스위치, 초기 허가 수, 장애 복구, 도구 재현은 [실행 문서](../docs/redis-product.md), 화면 개발에 필요한 필드와 재시도는 [API 계약](../docs/frontend/waiting-receipt-lifecycle.md)에 정리했다.

### 두 장비에서 확인한 고객 여정 한 회

캐시는 MacBook Pro, 앱 3대·PG·대기열 주·복제와 Sentinel 3개는 Mac mini에 두었다. 개인 SSH 터널 양끝에서 같은 Redis 실행 ID를 확인했다. 대상 A매장에 24명을 2초 동안 보냈고 24명이 모두 창 안에서 실제 전송을 시작했다. 첫 응답은 201이 23건, 202가 1건이다. 202를 받은 고객은 서버 안내에 따라 한 번 조회해 실제 번호를 확인했다. 24건 모두 클라이언트·PG 표·실제 식당 번호가 맞았고 중복·역전·유실은 0이었다.

## 발견하고 고친 문제

- 최초 DELETE 경계 검사에서 405를 확인해 소유자 검사를 포함한 철회·취소 경로를 연결했다. JSON 캐시 적중 시 날짜 오프셋이 UTC로 바뀌던 문제는 원래 서울 오프셋을 보존하도록 수정했다. 첫 전체 빌드의 MVC 슬라이스 10건은 추가 캐시 의존성이 없어 실패했다. 테스트 구성에 의존성을 추가하고 기존 계약 검사를 유지했다.
- Docker 내부 발생기가 밑줄이 든 컨테이너 이름을 HTTP Host에 그대로 넣어 400을 받았다. 연결 대상과 HTTP Host를 분리한 뒤 같은 소규모 표본을 확인했다.
- 초기에 Sentinel이 승격한 뒤 두 Redis 노드가 재시작 때 최초 역할로 되돌아갔다. 설정을 한 번만 초기화하고 Redis가 고쳐 쓴 역할과 Sentinel 설정을 쓰기 가능한 볼륨에서 읽게 수정했다. 맥미니 첫 작업은 여기서 멈췄으며 큰 부하 회차는 시작되지 않았다.
- 번호 발급 뒤 같은 매장 확대 명령을 다시 실행하면 PostgreSQL이 `ON CONFLICT` 전 발동하는 새 일자 검사에서 예외가 났다. 매장 잠금 후 기존 설정을 먼저 확인하게 수정하고 발급 전·후·원복 뒤 결과를 확인했다.

## 성능 판단과 보관

앞선 Redis OFF 제품 HTTP는 28회였고, 맥미니 장부 접수 비교는 33회였다. 이전 묶음 커밋의 3앱·1만 명/1초에서 세 회차 모두 1만 명이 첫 대기표를 받았고 최초 202 p95는 각각 5.082초·5.201초·5.390초였다. 이 값은 장부 접수 단계의 결과다. 새 워커가 실제 번호를 내주는 전체 경로는 1만 명에서 측정하지 않았다. 폴링 주기 2~10초, PG 발급 허가 2개, 캐시 장애 DB 우회 앱당 1개는 초기값으로 두었다. 접수 p95 1초·p99 2초, 번호 확인 p95 60초·p99 120초, B매장 회복 20초는 검토 후보로 남아 있다.

세 번째 독립 호스트와 실물 호스트 상실 시 정족수·복구 시간은 미확인이다. 두 개인 장비의 실험 전용 프로세스를 중지했고 공유 Docker 데몬과 사용자의 다른 컨테이너는 보존했다. 계약 문서는 백엔드 저장소에 있다. 프론트 범위 정정 전에 전용 작업트리와 패키지를 준비한 이력이 있고 프론트 소스 수정은 0건이다. Git 커밋·push·PR·팀 도구 발송·배포는 수행하지 않았다.

전체 변경을 임시 Git 인덱스에 올려 검사하면 이미 격리 DB에 적용한 V44·V46·V48의 마지막 빈 줄 세 곳에서 공백 경고가 나온다. 적용했던 마이그레이션 파일의 바이트를 보존했다. 컴파일·테스트·Flyway 검증은 통과했다.

원본은 이 작업트리의 `local-evidence/`와 맥미니의 `~/orca/experiments/catchtable-redis-product/20261122-product-ec9eabc9/`에 보관했다. 전용 DB 자격증명은 증거 묶음에서 제외했다. 회차별 지연과 대조 결과는 [검증 JSON](assets/2026-11-22-redis-product/verification.json)에 있다.

| PostgreSQL 중단 | 표 한 장을 접수한 뒤 전용 PG 프로세스를 중지했다. 기존 표 조회와 신규 신청 모두 503·재시도 2초를 받았다. 재시작 후 최초 키는 원래 표로 200, 중단 중 보냈던 신규 키는 순번 2로 202였다. 두 건 철회 뒤 미완료는 0이었다. |
| 세 VM의 주 노드 장애 | 각기 다른 Linux 커널·디스크에서 A에 캐시+Sentinel, B에 주+Sentinel, C에 복제+Sentinel을 배치했다. B 전체를 강제 종료하고 3.618초에 생존한 두 Sentinel의 합의와 C 승격을 확인했다. 종료 중의 두 202는 강제 종료 시작부터 4.226초에 실제 2·3번으로 확인됐다. B는 부팅 ID가 바뀌고 복제로 복귀했다. |
| 세 VM의 캐시 장애 | A 전체를 종료한 중에 DB 우회 3회와 식당 4번을 확인했다. 복귀한 A에서는 비영속 표식이 사라지고 Sentinel 정족수 3개가 복구됐다. 실험 고객 4명의 HTTP 표·PG 순번·번호 및 취소 결과가 일치했다. 물리적으로는 MacBook 한 대가 VM 세 대를 호스팅했고 앱·PG·발생기는 Mac mini에 있었다. |
| Docker 복구 실패 회차 | 기존 Docker 실험망에서 두 데이터 노드를 재시작한 후 40초 동안 표 4건이 미완료였다. Sentinel이 주 노드에 자기 호스트를 복제 대상으로 보낸 로그를 확인했다. 새 검증망에서 주소 재사용을 피하도록 고정 IP를 주고 실제 프로세스 중단·AOF 복원을 다시 확인했다. 실패한 DB의 표 4건도 그대로 재개해 3·4·5·6번을 대조했다. |
| 수정 전 힙 고갈 회차 | 합산 heap 768MiB에서 앱당 최대 4천 개의 비동기 HTTP 요청을 보관하도록 시험했다. 1만 건 모두 1초 안에 전송됐으나 JVM 세 대에서 힙이 고갈됐다. 최초 202는 80건, 장부 수락은 112건이었다. 같은 DB를 재시작 후 대조해 수락한 112건 전부 같은 키·표로 재조회했고, 모두 실제 번호를 받았다. 이 회차는 실패로 보관했다. |
| 최종본의 보호 상한 | 비동기 HTTP 보관 수의 상한을 해당 앱의 Tomcat 작업 스레드 수로 제한했다. 넘치는 요청은 기존 동기 처리로 진입한다. 실험의 앱 3대에서는 앱마다 최대 40개, 앱 1대에서는 최대 120개다. 접수 응답은 PG 커밋이 끝나야 반환한다. |

첫 3앱 대표 회차는 VM B가 주 노드였고, 장애 시험을 마친 뒤의 회차는 같은 규격의 VM C가 주 노드였다. VM은 각각 1 CPU·1GiB이며 게스트 간 복제와 Sentinel 투표는 전용 가상망을 사용했다. 두 물리 장비 사이의 앱 트래픽은 개인 SSH 터널로 전달했다. 대기열이 가득 찬 경우의 429, PG에서 확인할 수 없는 경우의 503과 동일 키 재시도는 기능 시험에서 따로 확인한다.

### 최종본의 부하 측정과 판정

CPU·heap·연결 풀 예산을 그대로 두고 앱 1대·3대의 실제 HTTP 응답과 PG 결과를 대조했다. 각 셀의 값은 실행 순서대로 표시했다. 처음 보낸 요청의 응답과, 같은 키로 재시도하거나 상태를 조회한 뒤 실제 번호를 처음 받은 시점은 각각 계산했다.

### 기능별 같은 JAR 비교

각 쌍은 같은 앱 3대와 입력으로 한 회씩 측정했다. 예약 조회·선점은 웨이팅 장부를 끄고, 웨이팅은 예약 캐시를 끄고 비교했다.

| 입력 | 설정 | 실제 창 내 전송 | 첫 응답 p95 (ms) | 슬롯 SQL 호출 | 실제 배정·번호 | B 오류 |

| 조회 1천/10초 | 기존 경로 | 1,000 | 7.26 | 1,270 | 공유 캐시 적중 0 | 0 |
| 조회 1천/10초 | 캐시 ON | 1,000 | 15.48 | 30 | 공유 캐시 적중 1239 | 0 |
| 조회 후 선점 300/2초 | 캐시 ON | 300 | 66.77 | 16 | 선점 201 12 · 409 26 | 0 |
| 조회 후 선점 300/2초 | 기존 경로 | 300 | 75.19 | 498 | 선점 201 12 · 409 18 | 0 |
| 웨이팅 1천/10초 | 기존 경로 | 1,000 | 44.88 | 270 | 클라이언트 번호 확인 1,000 | 0 |
| 웨이팅 1천/10초 | 장부·워커 ON | 1,000 | 46.69 | 288 | 클라이언트 번호 확인 1,000 | 0 |

조회 1천 건 비교에서 슬롯 SQL 호출은 1,270회에서 30회로 줄었고, 고객 조회 p95는 7.26ms에서 15.48ms로 늘었다. 두 장비 사이 SSH 전달을 포함한 합성 표본 한 회의 결과다.

캐시 ON에서 잔여가 보인 조회의 시작부터 선점 응답을 수신하기까지 http_201 12건 p95 180.34ms · http_409 26건 p95 181.63ms였다. 실제 배정 테이블 12개를 DB와 대조했다.

기존 경로에서 잔여가 보인 조회의 시작부터 선점 응답을 수신하기까지 http_201 12건 p95 164.87ms · http_409 18건 p95 247.28ms였다. 실제 배정 테이블 12개를 DB와 대조했다.
