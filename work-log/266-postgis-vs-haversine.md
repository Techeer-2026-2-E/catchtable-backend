# 지도 매장 조회: PostGIS 검토와 하버사인 유지 결정

- 작업일: 2026-11-07
- 이슈: [#266](https://github.com/Techeer-2026-2-E/catchtable-backend/issues/266)
- 기준: `feat/266-map-stores`, 기반 커밋 `dce5279`
- 측정 환경: 로컬 Apple Silicon(arm64) Docker, PostgreSQL 16.15, PostGIS 3.7.0, 일회용 컨테이너
- 나중에 기술 블로그 글의 재료로 쓸 수 있도록 판단 과정과 측정값을 함께 남긴다.

## 결론

PostGIS를 도입하지 않고 현재의 B-tree 사각형 + 하버사인 쿼리를 유지한다. 실제 매장 좌표 118,200건에서 PostGIS는 성능 이득이 없었고, 이미지 교체·마이그레이션·배포 DB 확인 비용만 늘어난다.

반경 1km 조회의 p95는 하버사인 4.56ms, PostGIS 15.40ms다(PostgreSQL 기본 설정, 로컬 측정).

## 배경과 PostGIS를 고른 이유

카카오맵 화면에서 매장을 조회하는 API 2개가 필요했다.

- 처음 화면: 현재 위치에서 반경 1km
- 이동·확대·축소 후: 화면 모서리 좌표로 만든 사각형 범위

기존 `GET /api/user/stores/home`은 [`NearbyStoreRepository`](../src/main/java/com/catchtable/store/repository/NearbyStoreRepository.java)에서 위경도 사각형으로 후보를 줄인 뒤 하버사인으로 거리를 계산한다.

PostGIS를 택한 이유는 두 가지였다.

- **대량 데이터 성능:** 초기 조사에서 PostGIS가 대량 데이터에서 빠르다고 판단했다. 당시 참고한 자료는 남아 있지 않다.
- **쿼리 통일:** 반경·사각형 조회를 `location` 컬럼 하나로 처리하고, 직접 작성한 하버사인과 극 근처 예외 코드를 없애려 했다. 이슈 초안에 적은 사유는 이쪽이다.

설계 초안은 `CREATE EXTENSION postgis`, `location` 생성 컬럼(`geometry(Point, 4326)`), GiST 인덱스를 담은 V36 마이그레이션과 `/home` 쿼리 교체였다.

## 맞닥뜨린 문제

### Apple Silicon에서 이미지를 받지 못함

`docker-compose.yml`의 이미지를 `postgis/postgis:16-3.5`로 바꾸자 컨테이너 생성이 실패했다.

```text
Image postgis/postgis:16-3.5 Error no matching manifest for linux/arm64/v8
```

PostgreSQL이나 PostGIS의 버전 호환 문제가 아니라, 이미지에 arm64 빌드가 없는 문제였다. 2026-11-07에 Docker Hub에서 확인한 결과는 다음과 같다.

| 이미지 | 지원 아키텍처 |
| --- | --- |
| `postgis/postgis:16-3.4` | amd64 |
| `postgis/postgis:16-3.5` | amd64 (`unknown/unknown`은 실행용이 아닌 빌드 증명 정보) |
| `postgis/postgis:16-3.6` | amd64 |
| `imresamu/postgis:16-3.5` | amd64, arm64 |

우회 방법은 있었다.

| 방법 | 확인 결과 | 부담 |
| --- | --- | --- |
| `postgres:16`에 `postgresql-16-postgis-3` 설치 | 일회용 컨테이너에서 설치와 `CREATE EXTENSION` 성공. 이번 측정에 사용 | Dockerfile 관리, 패키지 버전 고정 필요 |
| 커뮤니티 이미지 `imresamu/postgis` | arm64 제공만 확인, 실행하지 않음 | 공식 이미지가 아님 |
| `platform: linux/amd64` 에뮬레이션 | 시도하지 않음 | 로컬 DB가 에뮬레이션으로 실행됨 |

즉 이미지 문제만으로 PostGIS를 포기할 이유는 아니었다. 다만 감수할 가치가 있는지 판단하려고 성능을 먼저 측정했다.

### 기존 설계의 인덱스 문제

측정 중 V36 초안의 문제를 발견했다. `geometry` GiST 인덱스만 만들고 미터 단위 반경을 쓰려고 `location::geography`로 조회하면 **인덱스를 타지 않는다**. 실행 계획은 `Parallel Seq Scan`이었고 p95는 232.58ms였다. PostGIS를 쓴다면 geography 식 인덱스가 추가로 필요하다.

```sql
CREATE INDEX ON store USING gist ((location::geography));
```

## 테스트 방법

| 항목 | 내용 |
| --- | --- |
| 데이터 | 서울시 일반음식점 인허가 CSV의 `영업/정상` 매장 좌표 118,200건. 실제 적재 필터와 같은 건수이며 EPSG:5179를 WGS84로 변환. 이름·주소 등 좌표 외 컬럼은 더미 |
| 기준점 | 매장 위치에서 무작위로 뽑은 300곳. 모든 방식에 같은 순서로 사용 |
| 측정값 | 리터럴 값을 넣은 SQL을 DB 안에서 실행하고, 계획 수립과 실행을 합친 시간을 잼. 모든 컬럼을 text로 직렬화해 행을 실제로 읽게 함 |
| 라운드 | 기본 설정은 3라운드 중 첫 라운드를 제외한 2라운드, 병렬·JIT 끔은 2라운드 중 마지막 1라운드를 집계 |
| 시간 제한 | 방식·반경별 라운드당 15초를 넘으면 최소 30개 지점 후 중단. 그래서 느린 방식은 표본이 적음 |
| 설정 | PostgreSQL 기본값에 `shared_buffers=512MB`, `max_parallel_workers_per_gather=2`. 개발 DB와 분리된 일회용 컨테이너 |

### 비교한 쿼리

| 이름 | 방식 |
| --- | --- |
| 하버사인 (현재 코드) | `(latitude, longitude)` B-tree 사각형 + 하버사인 |
| 하버사인 전체 스캔 | 사각형 조건 없이 전체 행 계산 |
| `ST_DWithin` 타원체 | geography GiST + `ST_DWithin` + `ST_Distance` |
| `ST_DWithin` 구 | 위와 같고 `use_spheroid=false` |
| geometry + 구 거리 | geometry GiST `&&` 사각형 + `ST_DistanceSphere` |
| KNN | geography GiST + `ST_DWithin` + `ORDER BY <->` |
| 인덱스 미사용 | geometry GiST만 두고 `location::geography`로 조회 |

반경 조회는 `id`, `name`, `category`, `address`, `waiting_available`, `image_url`, 거리를 거리순으로 `LIMIT 10` 조회했다. 사각형 조회는 거리 대신 위경도를 조회했고, 정렬 없이 범위 안 전체를 반환했다.

## 결과 해석

아래 원인 분석은 실행 계획과 설정별 측정값에서 추론한 것이다. 병렬과 JIT의 영향을 따로 나눠 측정하지는 않았다.

1. **병렬 실행 비용:** 1km 조회에서 PostGIS 쿼리는 `Parallel Bitmap Heap Scan`을 썼고 하버사인 쿼리는 일반 `Bitmap Heap Scan`을 썼다. 플래너 비용도 41,737과 3,330으로 차이가 컸다. 병렬·JIT를 끄면 PostGIS p50이 13.51ms에서 2.45ms로 줄었다. 이 비용은 기본 JIT 기준(100,000)보다 낮아 1km에서는 병렬의 영향으로 본다.
2. **거리 계산 비용:** 병렬을 꺼도 타원체 계산은 하버사인보다 약 2배 느리다. 구 계산으로 바꾸면 p50이 2.45ms에서 1.73ms로 줄었다.
3. **인덱스 이점이 작음:** 현재 코드도 B-tree로 후보를 먼저 줄인다. 사각형 조회에서 GiST와 B-tree의 p50 차이는 약 10%다. 같은 설정에서 현재 코드의 p50도 실행 묶음에 따라 2.27ms와 1.09ms로 달라졌으므로 작은 차이는 의미를 두지 않는다.

"PostGIS가 빠르다"는 주장은 주로 인덱스 없는 계산과 비교할 때 맞다. 조사한 공개 자료 중 수치가 있는 [비교 글](https://aimagicdirectory.pages.dev/blog/why-postgis-matters-for-directories)도 앱에서 전체 행을 계산한 경우였고 측정 환경이 없었다. B-tree 사전 필터와 비교한 신뢰할 만한 벤치마크는 찾지 못했다.

KNN은 병렬·JIT를 끄면 가장 빨랐다. 다만 첫 페이지만 측정했고, 기본 설정에서는 다른 PostGIS 쿼리와 비슷하게 느렸다. 기본 설정에서 이 속도를 내려면 설정 변경과 추가 검증이 필요하다.

## 판단과 실제 변경

| 비교 항목 | 하버사인 유지 | PostGIS 도입 |
| --- | --- | --- |
| 반경 1km p95 (기본 설정) | 4.56ms | 15.40ms |
| 사각형 조회 | 기존 B-tree로 충분 | 약 10% 빠름 |
| 거리 정확도 | 1.1km 이내에서 타원체와 최대 2.60m 차이 | 타원체 기준 |
| 코드 | 하버사인·극 근처 처리 유지 | 내장 함수로 단순화 |
| 환경 | 변경 없음 | arm64 대응, 마이그레이션, 팀원 컨테이너 재생성, 배포 DB 확인 |

쿼리 통일이라는 장점은 있지만, 측정된 성능 이득 없이 환경 부담을 늘릴 만큼은 아니라고 판단해 하버사인을 유지한다.

- 지도 API는 기존 위경도 컬럼, `idx_store_location`, 하버사인 쿼리로 구현한다.
- V36 마이그레이션은 만들지 않는다.
- `docker-compose.yml`과 `.github/workflows/ci.yml`의 이미지는 `postgres:16`으로 유지한다.

## 검증과 한계

측정에 쓴 일회용 컨테이너는 삭제했고, 개발 DB는 사용하지 않았다. 측정 스크립트는 저장소에 넣지 않았다. 이번 작업은 문서 추가이므로 앱 테스트는 실행하지 않았다.

- 로컬 단일 접속 측정이다. 네트워크·JDBC 시간과 동시 접속 부하는 포함하지 않았다.
- 배포 서버, PostGIS 3.5, amd64 환경에서는 측정하지 않았다. 프로젝트에서 쓰려던 3.5 대신 3.7로 측정했다.
- 앱의 prepared statement와 달리 리터럴 값으로 실행했다.
- 좌표 외 컬럼은 더미이고, 실제 `store` 테이블의 전체 스키마가 아니다.
- 표본이 적은 항목의 p99는 참고용이다.
- `OFFSET`이 큰 뒤쪽 페이지는 측정하지 않았다.
- 100만 건 측정은 실제 데이터 규모와 달라 중단했고 결과를 쓰지 않았다. 수십만 건 이상에서 어느 쪽이 빠른지는 확인하지 못했다.

## 남은 점

- 이슈 #266 본문을 하버사인 기준으로 고쳐야 한다.
- 지도 API의 넓은 범위 응답 시간과 크기를 측정해 `LIMIT`과 축소 한도를 정한다.
- 폴리곤 검색 같은 공간 기능이 필요해지거나 데이터가 크게 늘면 다시 검토한다. 이때는 geography 식 인덱스와 병렬 설정을 함께 측정한다.
