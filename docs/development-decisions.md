# 개발 의사결정 기록

최초 작성: 2026-10-11. 로컬 구현을 팀에 공유하기 위한 기록이며, 후속 변경과 검증은 날짜별로 남긴다.

## 점주 대기 목록 실시간 갱신 — 확정

- 결정: SSE를 사용한다. 사용자 확인: “sse로 해”.
- 대안: 주기적 폴링. 구현은 단순하지만 갱신 지연과 반복 조회가 생긴다.
- 구현: 기존 회원별 SSE 연결 및 커밋 후 알림 전달을 재사용한다. `WAITING_CHANGED` 이벤트의 `targetId`는 매장 ID다. 고객 정보는 이벤트에 담지 않고, 프런트가 해당 매장의 목록을 다시 조회한다.
- 구독: `GET /api/owner/stores/{storeId}/waitings/subscribe?memberId={ownerId}`. 기존 EventSource 방식에 맞춘 임시 회원 식별이며, 점주 유형과 매장 소유권을 검사한다. 인증 도입 시 회원 ID 입력을 인증 세션으로 교체한다.
- 최초 `connect` 이벤트와 재연결 후에도 목록을 재조회한다. 이벤트 재생은 제공하지 않는다. 기존 메모리 SSE 저장소를 사용하므로 여러 서버 인스턴스로 확장할 때 전달 구조를 바꿔야 한다.
- 목록은 `GET /api/owner/stores/{storeId}/waitings`, `X-Member-Id` 헤더로 조회한다. 한국 시간의 당일 진행 중 팀을 대기번호 순서대로 반환한다.
- 프런트 배열 형식과 `id`, `waitingNumber`, `partySize`, `customerName`, `createdAt` 이름을 따른다. `compatibleTables`는 사용 가능한 설정의 테이블 중 인원 범위가 맞는 테이블이다. 실제 빈자리 여부는 점주가 확인한다.

## 미응답·노쇼 종료 상태 — 확정

- 프런트 `dev`의 `WaitingStatus`에는 `NO_SHOW`가 있고 `EXPIRED`, `CONFIRMED`는 없다. 점주 화면의 “미응답 노쇼”와 고객 화면의 호출 시간 만료 모두 `NO_SHOW`로 처리한다. 현재 두 화면은 목업 상태다.
- 결정: 사용자 확인 “백엔드도 NO_SHOW로 통일”. 백엔드 상태를 `EXPIRED`에서 `NO_SHOW`로 바꾼다.
- 대안: `EXPIRED`를 유지하고 프런트에서 변환하면 기존 백엔드 호출부 영향이 적다. 선택한 방식은 프런트와 종료 상태 이름이 같지만, 동료의 자동 만료 구현도 `NO_SHOW`로 맞춰야 한다.
- `CONFIRMED`는 고객의 도착 응답 상태여서 유지한다. 프런트는 진행 중 상태 판정에 이를 추가하거나 호출 화면으로 매핑해야 한다.
- 종료 사유는 `NO_RESPONSE`, `NO_SHOW`, `AUTO_EXPIRED`를 구분한다. 최초 종료 시각과 상태를 유지하며, 정정 전후 사유·설명·처리자·시각을 `waiting_end_history`에 남긴다. 같은 사유와 설명의 재시도는 이력과 알림을 중복 생성하지 않는다.
- 기존 `EXPIRED` 행은 `NO_SHOW`로 마이그레이션한다. 과거 상세 사유와 종료 시각은 알 수 없으므로 `LEGACY_EXPIRED`로 표시하고 시각은 임의로 채우지 않는다.
- 기존 고객 SSE 이벤트명 `WAITING_EXPIRED`는 유지한다. 이 이벤트를 받은 뒤 조회하면 상태는 `NO_SHOW`다. 이벤트명 변경은 호출 알림 담당자의 기존 계약에 영향을 주므로 이번 상태 변경에 포함하지 않는다.
- 프런트의 취소/노쇼 요청에는 아직 사유 입력이 없다. 기능 명세의 점주 취소 사유 및 사유 정정 이력을 위해 입력·요청 본문 연결이 필요하다.

## 동료 기능과 연결할 지점

- 호출·고객 응답·착석·고객 취소·자동 만료가 추가되면, 커밋 시 같은 `WAITING_CHANGED` 알림을 발행한다. 현재 개발 범위에서 신규 신청과 점주 종료가 발행 대상이다.
- 다음 팀은 점주가 수동 호출한다. 10월 6일 갱신된 기능 명세를 따르며, 이전 API 표의 자동 다음 호출 설명은 적용하지 않는다.
- 상태 변경은 웨이팅 행을 잠근 뒤 현재 상태를 확인한다. 자동 만료도 같은 행 잠금 또는 `WHERE status IN ('CALLED', 'CONFIRMED')` 조건부 갱신을 사용해야 한다. `version`은 늦게 저장되는 JPA 갱신이 확정 상태를 덮어쓰는 것도 방지한다.
- 호출 시각·타이머는 호출 담당 기능과 연결해야 한다. 이 변경은 호출 기능을 새로 구현하지 않는다.
- 10월 11일 머지된 리뷰 PR #79의 `V11` 다음으로 웨이팅 종료·이력 `V12`, 예약 선점 `V13`을 적용한다. 버전 번호 중복은 없다.

## 점주 종료 API

- 취소: `DELETE /api/owner/waitings/{waitingId}`, 본문 `{"reason":"매장 사정으로 접수 종료"}`, 성공 `204`. 진행 중 상태만 취소하고 이미 취소된 요청은 재처리하지 않는다. 최초 취소 사유를 보존한다.
- 미응답·노쇼: `POST /api/owner/waitings/{waitingId}/no-show`, 본문 `{"reason":"NO_RESPONSE","detail":"호출 후 응답 없음"}`, 성공 `200`. `reason`은 `NO_RESPONSE` 또는 `NO_SHOW`, 설명은 공백이 아닌 300자 이하다. 호출/응답 상태를 종료하거나 기존 `NO_SHOW`의 사유를 정정한다.
- 성공 응답: `waitingId`, `status`, `reason`, `detail`, `endedAt`. 종료된 건의 정정으로 고객 알림이나 다음 팀 호출을 다시 실행하지 않는다.
- 두 API 모두 `X-Member-Id`를 받고 점주 유형과 웨이팅의 매장 소유권을 검증한다.
- 프런트 취소 초안의 `POST .../cancel`은 API 명세의 `DELETE`로 변경하고 사유 본문을 추가해야 한다. 노쇼 요청에도 사유와 설명을 추가한다. 현재 프런트 화면은 API와 연결되지 않은 목업이다.

## P2 진행 범위 — 확정

- 결제·환불 이슈는 윤서 담당의 공통 결제 상태·멱등성·결과 재확인 계약과 먼저 맞추도록 지정되어 있다. 현재 `dev`에는 공통 결제 구현이 없다.
- 결정: 사용자 확인 “선점·예약 변경부터 진행”. 공통 결제 모델·결제 준비/승인·환불은 계약 확정 후 연결한다. 결제 결과가 불명확할 때의 선점 반환 조건은 이 계약에 맞춰야 한다.
- 기존 로컬 선점 코드를 최신 dev에 맞춰 옮긴다. 원래 작업 폴더는 보존하고 마이그레이션 이름은 현재 V12 다음의 V13으로 맞춘다. 선점 생성·조회·명시적 해제·시간 만료·재예약을 먼저 검증한다.
- 현재 선점에는 외부 결제 승인 처리가 연결되어 있지 않다. 결제 모듈을 연결할 때 승인 중/결과 불명의 예약을 자동 만료·해제로 반환하지 않도록 함께 연동해야 한다.

## 선점 구현의 경계

- 예약과 선점은 같은 행을 사용하여 활성 선점/확정 예약에 하나의 PostgreSQL 시간 중복 제약을 적용한다. 신규 배정·변경은 매장 설정을 공유 잠금으로 보호하고, 적합한 테이블을 `FOR UPDATE SKIP LOCKED`로 배정한다.
- 5분 기한은 서버가 판정한다. 조회 시 남은 시간은 0 이상이며 최초 만료 시각을 연장하지 않는다. 스케줄 정리 전에도 재예약 요청에서 만료 행을 반환한다. 확정된 예약은 선점 해제 API로 취소하지 않는다.
- 결제 연결 전인 현재는 선점 해제와 상태 전이가 DB 트랜잭션 안에서 끝난다. 외부 승인 요청이 진행 중이거나 결과를 모르는 경우의 반환 유예·결과 재확인은 결제 담당 구현과 함께 적용할 후속 항목이다.
- 웨이팅의 `NO_SHOW`와 예약 선점의 `EXPIRED`는 다른 상태다. 이번 `NO_SHOW` 통일 결정은 웨이팅에 적용한다.

## 최신 dev 반영과 결제 전 선점의 고객 내역 표시 — 확정

- 2026-10-11 21:05에 머지된 PR #76(고객 예약·웨이팅 내역), #79(리뷰 작성), #81(매장 상세 메뉴)을 로컬 작업 브랜치에 반영했다. 기준 커밋은 `69da7c2`에서 `2998442`로 갱신했다.
- 새 내역 조회는 예약 `CONFIRMED`만 진행 중으로 분류하여, 로컬에서 추가한 `PENDING_PAYMENT`가 종료 내역에 들어가는 문제가 있었다.
- 결정: 사용자 확인 “진행 중 내역에 표시”. 결제 전 선점 `PENDING_PAYMENT`와 확정 예약 `CONFIRMED`를 진행 중으로 분류하고, 만료된 선점 `EXPIRED`는 종료 내역에 포함한다.
- 대안: 예약 확정 전 선점을 내역에서 숨기면 확정 예약 중심의 화면을 유지할 수 있다. 선택한 방식은 결제 전 선점을 다시 찾기 쉽지만, 프런트에서 `PENDING_PAYMENT`를 결제 대기로 구분해야 한다. 결제 재개 동작은 공통 결제 계약 후 연결한다.
- 웨이팅 종료 내역의 상태도 기존 결정에 맞춰 `NO_SHOW`로 통일했다. 새 고객 내역 조회와 기존 예약 변경의 행 잠금·선점 만료 쿼리를 모두 보존했다.

## 코드 점검 후 수정 — 2026-10-11

- 선점 만료: 스케줄러가 DB 상태를 정리하기 전에도 `holdExpiresAt <= 서버 현재 시각`이면 고객 내역과 고객·점주 예약 조회에서 `EXPIRED`로 응답한다. 고객의 진행 중 내역에서는 제외하고 종료 내역에 포함한다. 만료 전 `PENDING_PAYMENT`는 진행 중 표시를 유지한다.
- 조회와 실제 만료 처리는 엔티티의 같은 판정 로직을 사용한다. 일반 내역·목록·상세 조회는 DB를 수정하지 않으며, 종료/만료 목록의 조회 후보에 아직 `PENDING_PAYMENT`로 저장된 선점도 포함한 뒤 같은 시각으로 최종 분류한다.
- SSE 재접속: 연결 목록 생성과 신규 연결 추가를 회원별 `ConcurrentHashMap.compute` 안에서 처리한다. 마지막 기존 연결의 삭제가 겹쳐도 새 연결이 저장소에서 분리되지 않는다. 이벤트 형식과 기존 SSE 연결 방식은 유지한다.

## 원격 변경과 순번 알림 연동 — 2026-10-15

- 로컬 작업의 기준을 최신 dev `6098cb4`로 갱신했다. 기존 P1과 예약 선점·변경 작업을 보존하고, PR #83의 알림 DTO와 PR #87의 리뷰 조회 변경을 반영했다.
- 알림 DTO의 `payload`와 기존 4개 인자 생성자를 함께 유지한다. 기존 문구 알림은 `payload: null`이며, `WAITING_CHANGED`의 `targetId`는 계속 매장 ID다.
- 아직 머지되지 않은 PR #86(`ec5a035`)의 순번 이벤트·payload·리스너·테스트를 로컬에 가져와 연결했다. 기존 `@EntityGraph` 조회 메서드 하나를 공유하여 중복 선언을 없애고, 종료 상태 테스트는 `EXPIRED` 대신 `NO_SHOW`를 사용한다.
- 점주 취소·미응답·노쇼로 실제 종료될 때 같은 트랜잭션에서 `WaitingQueueChangedEvent`를 발행한다. 커밋 후 남아 있는 고객에게 `WAITING_POSITION_CHANGED`를 보내며, 롤백·종료 재시도·사유 정정에는 순번 알림을 보내지 않는다.
- 이번 변경은 로컬에만 적용했다. PR #85는 수정하지 않았다. 이후 기능별 게시 시 PR #86의 머지 여부와 최종 코드를 다시 확인하고, 동료의 순번 알림 코드를 별도의 신규 기능으로 중복 게시하지 않는다.
- 검증: 별도 PostgreSQL 16 DB(`catchtable_fix`, 포트 `55435`)에서 관련 테스트 51건, 이어서 `./gradlew test assemble --no-daemon` 전체 214건/35개 테스트 클래스를 통과했다. 실패·오류·건너뜀은 0건이며 V1~V13 적용도 확인했다. 취소·미응답 이후 남은 고객의 순번 갱신, 재시도·사유 정정의 알림 중복 방지, 커밋 후 전송·롤백 시 미전송, 기존 알림 DTO 호환을 검증했다. 프런트 실제 연결과 결제 연동은 이번 검증 범위에 포함하지 않았다.
